# V2 Persistence Integrity Contract — Review Draft

**Status:** Proposed refinement of [D04](04-data-model-spec.md), not DDL and not proof of implementation. Names below identify logical relations and may change during owner review; key relationships and transaction behavior are required. Existing Open WebUI public contracts and AgentRuntime semantics remain governed by ADR-001/002.

**Unresolved security finding:** current V1 can publish after a direct grant revocation commits between its final check and publication. A lock-only prototype is also unsafe with a stale PostgreSQL repeatable-read snapshot, even if the lock query is the first SELECT. See the [reproduction and proposed authorization gate](04b-authorization-publication-race.md); the protocol below must be refined and proven against that finding before freeze.

## Isolated environment identity

- V2 uses a separately provisioned PostgreSQL database and a separate object bucket or disjoint, access-controlled object prefix. The index namespace is V2-only. It imports no V1 data or execution state.
- Bootstrap is a separately invoked, explicitly targeted operation. An empty target is initialized with an immutable environment ID and schema-generation marker; normal server/worker startup is read-only with respect to identity initialization. A missing marker, unexpected environment ID or unsupported schema generation fails closed. Startup must not create or overwrite a marker merely because the configured database or object namespace is empty.
- Operators configure an expected environment ID and the allowed V2 database and object namespace; startup verifies the persisted DB marker and independently verifies the matching object-namespace marker before accepting traffic. A marker is identity evidence, not a secret or permission grant. Database roles and object-store policies must restrict the process to the approved V2 resources. A copied marker or different alias for the same underlying database is insufficient evidence of isolation: provisioning and deployment tests must verify resource identity and access controls, not compare URL strings alone.
- No startup, test or bootstrap path may delete a V1 database or object prefix. Backup, restore, bootstrap and migrations are exercised on an explicitly disposable target; a production reset or cutover requires its separate approval.

## Relational ownership and keys

All published identities are immutable. IDs are globally unique opaque values; revision numbers are positive and unique per document. Composite keys are necessary to enforce ownership even when a caller supplies an otherwise valid ID from another document.

| Relation | Required key / constraints | Ownership rule |
|---|---|---|
| `documents` | PK `document_id`; nullable current revision represented by `(document_id, current_revision_id)` | The composite pointer must reference a revision of that same document. Publication must also check committed state; a foreign key alone cannot enforce a status predicate. |
| `revisions` | PK `revision_id`; unique `(document_id, revision_id)` and `(document_id, revision_no)`; FK to document; immutable checksum, object key and source metadata after commit | Revision Service is the only publication writer, including the first [ingested revision](03d-ingestion-contract.md). Insert the document parent before its first revision; update the current pointer only in the publication transaction. |
| `object_registry` | Unique canonical object key and checksum/size identity; object lifecycle, generation and deletion claim | Serializes all references to the same physical checksum-addressed object, even across documents. A checksum collision or key with different verified bytes is an integrity failure. |
| `staged_objects` | PK `stage_id`; FK to `object_registry`; immutable checksum; state, owner, expiry and lease/fencing metadata | Register the object and stage before object write, then write and read back bytes. A committed revision references a verified stage belonging to its document; deletion cannot race a live publication. |
| `upload_receipts`, `ingestion_jobs` | Receipt binds a V2-flow upload to principal, Open WebUI file ID, expected checksum/size and expiry; job binds principal/idempotency fingerprint, document, intended revision number, nullable committed-revision FK, source/index state and fencing generation | Document API owns receipt/job creation; a pre-commit job has no published revision FK. Historical V1 file IDs have no eligible receipt. Revision Service fills the revision FK and stores the durable idempotency outcome in the publication transaction. |
| `index_builds` | PK `build_id`; unique `(document_id, revision_id, build_id)`; composite FK to revision; parser/chunker/schema versions, source checksum, state, generation/fence | Build identity binds the exact revision and checksum. A partially written build is never active. |
| `active_indexes` | PK `(document_id, revision_id)`; composite FK `(document_id, revision_id, build_id)` to build; generation | Switching the pointer requires a READY build, matching source checksum and compare-and-set on generation, in one transaction. |
| `anchors`, `chunks`, workbook sheets/cells/merges | Build-scoped keys; composite FKs ensuring each parent belongs to the same build; unique deterministic ordinal or sheet/coordinate | Derived data must not refer to another build, revision or sheet. Parse evidence retains unsupported or failed units. |
| `previews`, `approvals` | Preview PK and document/base-revision FK; approval bound to preview, resource, base revision, patch hash, approver and fixed expiry | Approval is consumed at most once. A valid row alone does not replace a current authorization check. |
| `idempotency_records` | Unique `(principal_id, operation, idempotency_key)`; immutable request fingerprint and durable result reference | Same key and fingerprint returns the same outcome after current authorization; same key and different fingerprint conflicts. No local record proves an external operation happened exactly once. |
| `outbox` | PK `event_id`; unique domain operation/event identity; payload or immutable payload ref; delivery state | Written in the same transaction as the associated publication. Delivery is at least once; consumers deduplicate the stable event ID. |
| runtime bindings, runs, events, checkpoints, invocations | Conversation has one engine binding; every run has a matching binding; unique `(run_id, sequence)` and `(run_id, call_id)` | AgentRuntime remains owner; checkpoints are pinned to run, engine and tool/skill versions. Allocate event sequence atomically with event insert. |

Implement non-null, uniqueness, positive revision and referential constraints in PostgreSQL, not solely in application checks. Use a deferrable or two-step same-transaction relationship where the document/current-revision cycle requires it; never make an uncommitted revision visible to solve the cycle. A state-dependent invariant such as READY build or COMMITTED revision must be checked under locks in the publication transaction and protected against later mutation, not assumed from the FK.

## Publication and recovery protocol

1. Record a stage with a unique key, checksum, intended owner/resource and lease. Create the immutable object conditionally; read it back and verify checksum and size. A failed or ambiguous object-store write is reconciled by checking the exact object, never by assuming success.
2. Mark the stage verified only after successful verification. For an edit, Revision Service opens a DB transaction, locks the resource and approval, and rechecks current authorization, approval identity and expiry, canonical patch hash, verified stage and current base revision. For an initial ingestion, it instead rechecks current document-create/folder permission, verified stage and unique idempotency outcome; there is no edit approval or patch hash. It uses a conditional update or lock to prevent concurrent publication.
3. In that transaction, consume edit approval **when applicable**, insert immutable revision metadata, advance the document pointer, write the outbox event and persist the idempotent outcome. DB commit is the single public visibility boundary. A retry after commit and before acknowledgement rechecks current access and returns the same revision, not another publication.
4. Garbage collection follows the shared-object protocol below. An expired stage alone does not authorize physical deletion: the same checksum-addressed object can be referenced by other stages or committed revisions. Exact retention and legal-hold policy are separate operational configuration to lock before release.
5. If a committed object is absent or checksum-invalid, reads fail closed and alert operators. Repair restores the exact verified bytes through an auditable process; rollback publishes a compensating revision rather than rewriting history.

## Shared checksum-addressed objects and garbage collection

The following is a proposed safety protocol, not an implemented storage API. An object key identifies immutable bytes within the V2 namespace, and a physical object may be shared by multiple stages or revisions. The registry is the synchronization authority for that key; checking only the stage selected for cleanup is insufficient.

1. A writer first creates or locks the registry row for the canonical key and registers its stage/reference in the **same database transaction**, before issuing a conditional object-store write. The row is unique per physical key. Publication attaches the committed revision under that same row lock only after verifying its own authorized stage and checksum. A new reference cannot attach to a deletion-claimed generation. All writers, including restore, rollback, upload, editing and repair, must participate; reject a write if this cannot be established.
2. A collector locks the registry row and examines **all** committed-revision references, unexpired stage leases, active publication pins, retention/legal holds and unresolved writes for that key. It can mark a specific generation `DELETE_CLAIMED` only when none protect the physical object and the stage safety interval has elapsed. Publication and new reference creation must not proceed on that generation after the claim commits. No object-store call occurs while assuming a DB row lock survives a DB commit.
3. Object deletion occurs after the claim commits. The claim includes a fencing generation and, when supported, an exact object version/ETag for conditional deletion; the storage implementation must document its actual delete semantics. While deletion outcome is pending or unknown, creators of that key wait or fail closed. A stale collector cannot delete an object from a later generation. If the provider cannot ensure a delayed delete cannot remove a later write, do not reuse the physical key: use a unique immutable generation-qualified key and verify checksum separately, or use an equivalent provider-backed deletion fence. A DB token alone cannot fence an already-issued object-store request.
4. After deletion is confirmed, the collector conditionally records completion for the same generation. A later writer can create a new generation only when the old delete is known complete or provider semantics make a late old delete harmless. On uncertain delete, crash or timeout, keep the key quarantined and reconcile; never infer success from the absence of a response. Object-store listing or an apparent orphan is not by itself authorization to delete an unregistered object. A controlled inventory/reconciliation process handles unregistered objects without touching other namespaces.

Required tests use two independent documents/stages sharing identical bytes: expire one stage while another is live or committed, race stage creation and publication with a GC claim, and inject crash/unknown deletion outcomes. Verify no committed object disappears, no reference attaches to a claimed generation, delayed deletes cannot remove a subsequent generation, and both orphan cleanup and retries eventually converge when the object store becomes available. Test the actual configured storage backend's version/delete behavior; an in-memory store alone is not proof.

## Durable work and fencing

Each claim increments a monotonically increasing fencing token in the job/build row. A worker may renew, checkpoint, mark verified or publish only with the current token and an unexpired lease; every conditional update checks the token in the same transaction. A stale worker whose lease expired cannot mark a newer worker's build READY or switch the active pointer. A lease timeout permits a new claimant, not blind repetition of an external side effect. External unknown outcomes are quarantined for reconciliation when the provider cannot guarantee idempotency or reveal status.

Index build output remains scoped to `build_id` until verification checks source checksum, expected units and completeness proof. Activation uses a locked/CAS pointer update and emits an outbox event in the same DB transaction. A cursor binds the build and current access is checked on every request; retaining or retiring a build cannot silently redirect its cursor to another build. The proposed [D03c cursor lifecycle](03c-cursor-contract.md#ttl-rotation-and-build-lifecycle) requires the build collector to preserve a verified build for live cursor TTL plus an in-flight margin after its last issuance, or return an explicit retired-build error on emergency retirement. Record the last issuance durably if the collector relies on it.

## Required verification before implementation acceptance

- Disposable PostgreSQL tests: wrong-document current revision and wrong-revision active index violate composite FKs; duplicate revision numbers and outbox IDs are rejected; only one concurrent publication of the same base revision succeeds.
- Simulate claim expiry and a second worker: the first worker's checkpoint, READY transition and activation are rejected by fencing; a verified new build can activate exactly once.
- Fault injection before stage write, after object write, after verify, during DB commit, after commit before acknowledgement, during outbox delivery and during GC claim/delete. Confirm retry, cleanup and visibility at each boundary.
- Verify same-key/same-request replay, changed-request conflict, revoked permission on replay, fail-closed reads on missing/corrupt committed bytes and a compensating rollback.
- Exercise permission revocation both before and after the final permission check, including direct and inherited grants and both configured DB session-sharing modes. An earlier V1 PostgreSQL characterization covers only a direct grant revoked before the final check; it is not a proof of the remaining authorization/publication race.
- Run fresh bootstrap and backup/restore against a disposable V2 PostgreSQL database and disposable object namespace; test wrong/missing identity markers and privilege isolation. Passing SQLite tests is not PostgreSQL or object-store evidence.
