# Authorization / Revision Publication Race — Phase 0 Finding

**Status:** Reproduced against the current checkout on disposable PostgreSQL 17.6, then mitigated in the current V1 path for the tested direct-grant, role, deactivation and group-membership races. The V2 authorization contract and production gate remain open. This is not evidence that a running server has this patch or configuration.

The source-level [effective-authorization writer inventory](04c-effective-authorization-writer-inventory.md) adds the document-move path and identifies its stale route-admin flag. A PostgreSQL regression reproduced unauthorized move authorization after demotion before a fresh role read was added under the exclusive gate. Concurrent move serialization, external identity and direct database writers remain unverified.

## Current checkout follow-up (2026-11-12)

The current checkout now uses a PostgreSQL transaction-scoped advisory gate: Revision Service takes a shared lock before checking live account role and document write access and retains it through the publication commit; access-grant, group-hierarchy and role/deactivation writers take the exclusive lock in their own write transactions. Document move also takes the exclusive lock after any personal-root creation that may commit. Publication refuses transactions whose isolation is not `READ COMMITTED`, and a fresh scalar role read under the gate prevents an earlier ORM role snapshot from authorizing a commit. SQLite remains a local compatibility path without this PostgreSQL protocol.

On a newly created disposable PostgreSQL 17.6 container, the six previously failing direct-grant, admin-demotion and owner-deactivation cases plus the two earlier before-final-check cases now pass under both session-sharing modes. A group-membership removal after the final access check failed in both modes when the group writer did not take the gate, then passed in both modes after that writer took it. A separate regression failed without the isolation check and passed when `REPEATABLE READ` was rejected. An inherited-folder-grant variant passes in both session-sharing modes. The full `test_resource_indexing_postgres.py` module passed **33 tests**; `test_revision_publication.py` passed **24 SQLite tests** and `test_document_library.py` passed **7 SQLite tests**. These use isolated schemas, test users, in-memory staged bytes and controlled barriers. They do not verify every authority writer, live authentication, a separate V2 database, external identity changes, real object storage or staging. Direct SQL by a database role capable of bypassing the gate remains outside the tested protocol. Phase 0 and release gates remain false.

## Reproduction and observed result

`test_permission_revoked_after_final_check_must_prevent_commit_in_postgres` in `packages/backend/tests/test_resource_indexing_postgres.py` creates a document, a verified preview and a direct user write grant in an isolated schema. The test pauses publication immediately after the second, successful `accessible_document(..., 'write', lock=True)` check, calls the production `AccessGrants.set_access_grants` method with an empty grant list in another transaction, waits for it to commit, and then lets publication continue. The subject is not the owner or an admin. Group lookup is stubbed to an empty list, and staged bytes use an in-memory store.

On this checkout, the direct-grant method and both `DATABASE_ENABLE_SESSION_SHARING=True` and `False` produced a committed revision instead of denying publication: **2 tests failed, `DID NOT RAISE HTTPException`**. The grant revocation had committed before the publication was allowed to continue. The preceding test that revokes *before* the final authorization check passes; it does not cover this window. No production database, user or object store was used.

The test permits a correct implementation to serialize publication before revocation: if revocation waits for an authorization lock held by publication, the publication may commit first and the revocation then completes. If revocation commits first, publication must instead fail without consuming approval, advancing the pointer or writing an outbox event. Both outcomes preserve a defensible order; a grant revoked and committed before publication must not be used by the later commit.

## Root-cause evidence and scope

`revision_service.commit_preview` checks current write access twice, then inserts publication records and commits. The document row is locked, but the existing direct-grant deletion is not serialized with that document lock. A successful access check is therefore only a point-in-time read, not a lock or atomic authorization/publication boundary. This finding covers the direct-user-grant scenario and the controlled pause in the test; other policy inputs and deployments need their own tests.

The current API paths update document/folder grants through `AccessGrants`, and `get_async_db_context` may use a separate session when session sharing is disabled. Group membership, nested folder grants, roles, and any other authority inputs can also change effective permission. Locking only a single direct grant row would not address all of these paths. Do not claim production readiness or zero unauthorized commits from the earlier pre-check revocation test.

## Reproduction: admin demoted during publication

`test_admin_demoted_during_commit_must_prevent_publication_in_postgres` seeds a non-owner user with admin role and captures the role as the route does. It pauses the real revision service during staged-byte reading, changes that user to `user` via `Users.update_user_role_by_id` in another transaction, waits for the role change to commit, and then lets publication continue. There are no direct or group grants; group resolution is stubbed to an empty list and staged storage is in memory. The test uses the actual `commit_preview` and real PostgreSQL user-role mutation, but does not exercise authentication middleware or the HTTP route.

At baseline, both `DATABASE_ENABLE_SESSION_SHARING=True` and `False` failed with `DID NOT RAISE HTTPException`: the service returned after the demotion rather than refusing to publish. This is a separate controlled case from direct-grant revocation. The regression now passes with the current-checkout gate, but must not be treated as a passing production gate. A proper implementation may serialize the demotion after an already-authorized publication, but when the demotion has committed first it must not publish based on the captured boolean.

## Current authorization inputs and mutation entry points

The following is a targeted source audit, not proof that all writers have been found. It provides concrete integration obligations for the proposed gate:

| Input to publication authorization | Current read and write paths | Implication for V2 |
|---|---|---|
| Document and folder grants | `library.has_document_access` checks `mh_document`, then walks `Document.folder_id` and `Folder.parent_id` checking `mh_folder`; `routes.update_document_access` and `update_folder_access` call `AccessGrants.set_access_grants` | Grant replacement, revocation and any other grant writer must acquire the gate in its own write transaction; `set_access_grants`, `set_access_control` and `revoke_all_access` currently commit internally. |
| Membership and group hierarchy | `library._groups_for` requests inherited groups. `Groups.set_group_user_ids_by_id`, `remove_user_from_all_groups`, `sync_groups_by_group_names`, `add_users_to_group`, `remove_users_from_group`, `update_group_by_id` and group deletion change memberships, hierarchy or group grants. Group routes and SCIM invoke group mutation methods. | `hierarchy_transaction` creates its own DB session and takes PostgreSQL advisory lock `731947205`; passing a caller session to a group method does not make these changes part of the caller transaction. Gate acquisition and existing advisory-lock order must be specified together and tested for deadlocks. Socket disconnect after group commit is not a transaction barrier. |
| Folder topology and owner | `has_document_access` grants access via a document owner or any ancestor folder owner; `library.move_document` changes the parent folder and commits. | Move and any supported owner/folder topology mutation must serialize with publication, including paths outside the visible Mini-Hermes router. For PostgreSQL, the permission read must use a transaction isolation/snapshot policy that sees a revocation committed before the shared gate is acquired. In particular, acquiring a lock after an earlier repeatable-read snapshot can retain stale authorization even if writers correctly serialize. The proposed design must specify and test isolation, identity-map refresh, implicit commit behavior, and both session-sharing modes rather than assuming the lock alone refreshes state.

## Proposed V2 design to review before freeze

Use a transaction-bound authorization epoch gate in the same V2 PostgreSQL database as revision publication. Auth Service retains authority for identity and permission decisions; this is a synchronization protocol across its module and Revision Service, not delegation of approval to AgentRuntime.

1. Every mutation that can change effective document authorization—including direct and inherited grants, folder moves, group membership/inheritance and relevant role changes—acquires an exclusive lock on a shared authorization gate **before** changing authorization state and retains that lock until its transaction commits or rolls back. All supported mutation paths must participate; paths that cannot participate must make affected document commits fail closed.
2. A publication transaction acquires a compatible shared lock on that same gate **before** reading current authorization and retains it through the revision publication commit or rollback. Permission data and the check are read through the transaction-bound Auth Service interface; the final check must not silently switch to an independent session. Visibility of a committed revocation requires the separately verified isolation policy below; a concurrent compliant writer cannot commit a revocation in the check-to-publication window.
3. Adopt a consistent lock order: authorization gate first, then document, preview/approval and publication rows. Audit every mutation and retry path for the same order and for helpers that commit implicitly. Database roles must prevent alternative writers from bypassing the protocol. A global gate is the initial correctness-oriented design for the 10–20-user deployment; finer-grained gates require an independently verified protocol for cross-resource and inherited permissions.
4. If current authorization cannot be evaluated under the gate—for example, an external authority or cache cannot supply transactionally valid current state—deny publication. Do not rely on a prior LLM assertion, token-carried authorization snapshot, successful cursor, or provider retry.

The current V1 path implements the core PostgreSQL lock, role refresh and isolation guard described above. The complete V2 protocol is not accepted or verified. It assumes the authoritative authorization state and every mutation path can participate in the same PostgreSQL locking protocol. Validate that assumption against Open WebUI ownership and all external identity flows before freeze; if it is false, design and test an equivalent linearizable authorization lease/version barrier rather than silently weakening the guarantee. Permission expiration and approval expiry also require a separately verified publication-time policy; a row lock cannot stop time.

## Test-only gate prototype

Four disposable PostgreSQL tests exercise the proposed shared/exclusive gate with both session-sharing modes. When publication takes the shared gate first, the revocation transaction waits and observes revision 2 only after publication commits. When revocation takes the exclusive gate first, publication waits, then the actual `commit_preview` rejects the revoked user without advancing the revision or consuming approval. The tests inspect PostgreSQL lock waits and use separate transactions; 4 passed on PostgreSQL 17.6.

A further four PostgreSQL 17.6 prototype cases compare `READ COMMITTED` and `REPEATABLE READ` when the revoker exclusively locks an unchanged gate row and commits deletion of a grant. With a snapshot established before acquiring the gate, the repeatable-read transaction still sees the old grant after revocation, whereas read committed sees the deletion. More subtly, the same stale result occurs when `SELECT ... FOR SHARE` on the gate is the reader transaction's **first SELECT**, but it starts while the revoker holds the exclusive lock: its repeatable-read snapshot predates the revoker's commit even though the lock returns afterward. The test observes the actual PostgreSQL lock wait and uses a raw SQL count to avoid ORM identity-map effects. No gate-row version is updated in this prototype.

A separate `READ COMMITTED` test keeps a `User` ORM object loaded in a reader session, commits a role demotion under the test gate in a writer transaction, then acquires the shared gate. With session sharing enabled, the actual `Users.get_user_by_id(..., db=reader)` returns the cached old role; a `select(User).execution_options(populate_existing=True)` in that transaction sees the new role. This demonstrates an identity-map hazard for a future transaction-bound check; it does not establish that the current commit path performs this particular reread. Fresh SQL semantics, object refresh and all permission inputs must be verified together under the accepted protocol.

The simple lock-only design must therefore not claim correctness under arbitrary isolation. A candidate is to require PostgreSQL `READ COMMITTED`, acquire the shared gate first, then execute fresh transaction-bound authorization reads while holding it; verify actual connection isolation and fail closed if it differs. An alternative isolation/version protocol requires its own proof, including a waiter that starts before revocation commits. The tests do not prove all ORM/cache paths, distributed authorization or production behavior.

These earlier prototype tests acquire a separate test-only row lock around the existing service. The current-checkout implementation instead uses a PostgreSQL advisory transaction lock. Group lookup is stubbed in the prototype and storage is in memory. The prototype remains only feasibility evidence; the newer production-path regressions are described at the top of this document.

## Required evidence

- Keep the reproduced regression executable in both session-sharing modes. Do not hide a future failure or convert it into an expected production outcome.
- Test direct and inherited grants, group membership changes, folder moves, relevant role changes, unavailable authorization, and both revocation-before-publication and publication-before-revocation serializations using separate PostgreSQL transactions and deterministic barriers.
- Check no unauthorized committed revision, approval consumption, pointer update or outbox event; test crash/cancellation and lock-order deadlocks. Verify the same invariants with the actual staged object store and in staging.
- Update contract catalog, transaction ownership, public compatibility tests and deployment/rollback plan together. The observed SQLite and PostgreSQL tests alone do not approve a V2 rollout.

## Reproduction: document owner deactivated during publication

`test_owner_deactivated_during_commit_must_prevent_publication_in_postgres` pauses the real `commit_preview` during staged-object reading for an authenticated document owner, then invokes `Users.update_user_by_id` in a separate transaction to change the account role from `user` to `pending`. After that change commits, publication continues. Both session-sharing configurations fail because publication succeeds instead of refusing the now-deactivated owner (**2 failures, DID NOT RAISE HTTPException** on disposable PostgreSQL 17.6). The test uses in-memory object storage, does not exercise SCIM or authentication middleware, and permits publication first when the two operations are correctly serialized.

This is distinct from the admin-demotion case: `has_document_access` accepts ownership without reading account status. `get_verified_user` rejects `pending` at request authentication, but that earlier check is not a publication-time check. The SCIM update and patch paths call `Users.update_user_by_id` with `role=pending` for a non-admin deactivation; the test exercises that model mutation rather than the HTTP route. A current role/active-account check must therefore apply to **every** principal, including owners and users with direct or inherited grants, under the same transaction-bound authorization protocol. Audit and synchronize `update_user_by_id` and all other role/deactivation/deletion writers, not only `update_user_role_by_id`; account deletion also removes group membership through a separately owned transaction before deleting the user. These observations do not establish that the production server runs this checkout.
