# V2 Ingestion and Initial Revision Contract — Review Draft

**Status:** Proposed Phase 0 internal contract. It refines [D02](02-architecture-spec.md), [D03](03-contract-catalog.md), [D04](04-data-model-spec.md), [D04a](04a-persistence-integrity-contract.md), [D05](05-coverage-semantics.md) and the observed [Open WebUI file boundary](07c-file-upload-contract-inventory.md). No V2 API, storage schema or worker is implemented by this document. Public URL/status mapping awaits D07 compatibility review.

## Ownership and scope

An R1 ingestion request creates **one new V2 document** with first revision. It never replaces an existing revision or imports V1 persisted document state. Later content changes require the approved Revision Service patch/commit path. Open WebUI authenticates the principal; Document API accepts the upload and validates format, size and input; document storage stages and verifies immutable bytes; Revision Service alone publishes the first revision and current pointer; Document Worker parses and indexes that committed source. AgentRuntime may request inspection or task status through Document API but cannot write document DB or object storage.

The V1 `/api/v1/files/` response remains an Open WebUI file acknowledgement. A `mini_hermes_chat_upload` flag and best-effort library adoption are not V2 ingestion success. If V2 accepts an Open WebUI file as a source, that file must have been **newly uploaded through the V2 flow** and have a durable, authenticated upload receipt binding principal, file ID, expected checksum/size and V2 flow version. An arbitrary historical V1 file ID is rejected; this path must not become a legacy-data import or backfill. V2 reauthorizes current ownership/access, reads actual bytes, verifies the receipt's checksum/size, and copies them into the isolated V2 namespace. An Open WebUI file ID alone is neither a V2 document ID nor an immutable source proof. A user may also upload bytes directly through a separately versioned V2 endpoint after its public mapping is reviewed; the same internal protocol applies.

## Internal command and result

`start_ingestion(principal, source, filename, content_type, idempotency_key, target_folder?)` uses a trusted principal and byte stream or an authorized source-file reference. `source` is a tagged union, never an arbitrary filesystem path or model-supplied storage key. Validation checks the allowed R1 suffix and actual file signature/container, encrypted/corrupt/zip-bomb/resource limits, and folder write permission where applicable. MIME and filename are hints, not authority. The service computes SHA-256 and byte length from the bytes it actually stages; client `file_hash` metadata is advisory and must match or be rejected if the API accepts it. No implicit content conversion or legacy format fallback.

The command's durable idempotency scope is `(authenticated_principal_id, start_ingestion, key)`, using [D03b](03b-idempotency-hash-contract.md). Its canonical request fingerprint binds an **expected** source SHA-256 and size, normalized filename/content type, target folder and V2 environment identity. A source-file reference also binds its Open WebUI file ID and version/ETag when available. The expected checksum/size are required request assertions, never trusted as proof: first execution reads the source bytes and verifies them before stage verification. A first short DB transaction reserves the unique idempotency key/fingerprint and allocates a hidden document parent and durable job **before** any object-store effect; concurrent same-key calls attach to that job, while changed fingerprints conflict. A worker can recover a reserved job after a crash. A retry with the same key and assertions reauthenticates and reauthorizes the pending job or resulting V2 document, then returns its durable outcome without needing the mutable Open WebUI source to remain available. A changed checksum/size, source ID/version or other semantic input under the same key conflicts. This makes a retry after source deletion deterministic without accepting different bytes under the same request. Same key and same fingerprint returns the same `job_id`, `document_id` and first revision, including crash after DB commit but before acknowledgement. A missing key is rejected for this durable command. Keys persist beyond the job/reconciliation window; expiry cannot turn an unknown side effect into a duplicate document.

Accepted result: `job_id`, `document_id`, `revision: 1`, `source_sha256`, `source_state`, `index_state`, and a status reference. Before `COMMITTED`, these IDs identify only the authorized pending operation; they are not a publicly readable revision. The response may be accepted while source publication or indexing is pending; it cannot say `READY` solely because Open WebUI returned a file ID. `get_ingestion_status(job_id)` reauthenticates and checks current job ownership and create/folder scope before publication, then current document access after publication; it returns the [proposed status schema](schemas/ingestion-status.schema.json) only to an authorized caller. Read/search reports an existing job ID with `INDEX_NOT_READY` until an eligible active build exists; it never schedules or retries ingestion implicitly.

## Source and index transitions

Source and index have separate state and evidence. Source follows `STAGED → VERIFIED → COMMITTED → AVAILABLE`, or a terminal failure before commit. `STAGED` means an object write has been requested; `VERIFIED` requires reading back exact stored bytes and checking size/checksum. Revision Service commits revision row, current pointer, idempotency outcome and outbox event in **one PostgreSQL transaction**. For an initial upload, explicit user upload plus current create permission is the authorization basis; there is no document-edit approval or patch hash. `COMMITTED` is the public revision visibility boundary: document lists and read tools exclude the pending document before it, even if a parent row was allocated for the job. `AVAILABLE` means post-commit integrity was checked; it is not another publication transaction. A committed revision whose object is missing or corrupt remains in history but all content reads fail closed with `INTEGRITY_FAILURE` and alert.

Index follows `NOT_REQUESTED → REQUESTED → RUNNING → VERIFYING → READY`, or `FAILED`, independently of source publication. The ingestion job/outbox schedules exactly one intended build identity for `(document, revision, source checksum, parser/chunker/schema versions)` under its idempotency key. Worker claims are fenced by a durable generation and lease; stale workers cannot checkpoint, mark READY or switch the active pointer. `READY` requires a verified build manifest and coverage proof against the immutable source, then a transactionally updated active pointer and outbox event. Rebuilds use new build IDs and must not overwrite a previous build or redirect its cursors. Parser, index, analysis and LLM-context completeness remain distinct even when the index is READY.

Failures before source commit may leave a staged object; its registry claim and safety interval govern cleanup. A failed index never makes a committed source disappear; status can say source `AVAILABLE` and index `FAILED`, with a safe problem code and explicit retry operation. Retry of a failed build is a separate idempotent command that creates a new build attempt, not a side effect of read/search. Crash after source commit before response returns the same revision; crash after object write but before verification checks exact stored bytes before continuing. An unknown external storage outcome is reconciled by object identity/checksum and fenced registry state, never blindly repeated.

## Status and evidence rules

Status reports both state machines and immutable identity. `source_sha256` is present only after bytes have been verified; `index_build_id` is null until a build is recorded. `parser_coverage` and `index_coverage` are independently nullable proofs under [D05](05-coverage-semantics.md). `READY` requires both proof records but does not set either `complete: true` by implication. `integrity_status` separately reports `UNKNOWN`, `VERIFIED` or `FAILED`; a previously available source whose committed bytes later become corrupt retains its revision history but cannot be read. A status check can report a safe failure without revealing inaccessible document existence. UI labels must distinguish uploaded, source available, indexing, ready, partial coverage and failed. Model context receives bounded references/evidence, not the entire upload.

Before freeze, owners must set exact file/resource ceilings, upload transport and public versioned path, receipt lifetime/consumption semantics, operation-specific hash normalization, worker lease and retry policy, status HTTP mapping, stage retention, and storage provider guarantees. Contract tests must cover duplicate and changed-key uploads, rejection of an unreceipted historical V1 file ID, source-file authorization/revocation, forged client hash, corrupt/oversized/encrypted input, object readback mismatch, every crash boundary, stale worker fencing, failed index with available source, active-pointer CAS, status disclosure and no implicit read-triggered job. The Phase 2 vertical slice must pass through the real Open WebUI → AgentRuntime → Document API V2 → XLSX Engine → tool result → UI boundaries on disposable infrastructure.
